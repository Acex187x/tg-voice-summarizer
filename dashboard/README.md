# Дашборд истории Telegram (чтение по запросу)

Приватный просмотр истории, которую сохранил бот: последние сообщения,
сообщения по чатам, поиск по тексту, голосовые с расшифровками и сводками,
сводки чатов. Только чтение.

## Чем отличается от первой версии

Первая версия (`/root/served/tg-history-dashboard`, сентябрь 2026) копировала
все таблицы Convex в локальный SQLite через `_system/cli/tableData`: сначала
раз в минуту, потом раз в 10 минут и раз в неделю целиком. Convex списывает
Database I/O за каждый прочитанный документ, поэтому за один период это дало
92 ГБ из 97 ГБ всего проекта.

В этой версии:

- нет фонового цикла, таймеров, cron и локальной базы. Сервер не обращается к
  Convex, пока его не попросит браузер;
- браузер грузит данные при открытии страницы и по кнопкам «Обновить»,
  «Загрузить ещё», выбору чата, поиску (Enter) и открытию карточки. В
  `app.js` нет `setInterval`/`setTimeout`, это проверяет тест;
- каждый запрос — одна internal-функция из `convex/dashboard.ts`. Она читает
  одну страницу по индексу (`by_chat_ts`, `by_chat_message`, `by_chat_ack`,
  `by_voice_settings`, `by_settings`, поисковый индекс `search_text`) с
  фиксированным размером: 50 сообщений, 30 голосовых или 20 сводок.
  `messageEmbeddings` не читается никогда;
- каждый ответ содержит `readBytes`: JSON-размер прочитанных документов, то
  есть примерную оценку Database I/O этого вызова. Дашборд показывает сумму
  за вкладку и вес последней страницы.

## Сколько читает одна загрузка

Средние размеры документов взяты из старого локального зеркала (снимок
ноября 2026): `chatMessages` ≈ 333 Б, `voiceMessages` ≈ 1,7 КБ (максимум
116 КБ), `chatSummaries` ≈ 8,4 КБ, `chatIndexStats` ≈ 0,7 КБ,
`chatImportJobs` ≈ 1,7 КБ.

| Действие | Что читается | ≈ объём |
|---|---|---|
| Открыть страницу | список чатов (`chatIndexStats` ~20 строк, `chatImportJobs` ~7, по последнему голосовому на чат без названия из импорта) + 50 последних сообщений | ≈ 60 КБ + 17 КБ ≈ **80 КБ** |
| Выбрать чат / следующая страница | 50 сообщений по `by_chat_ts` | ≈ **17 КБ** |
| Поиск | 50 результатов из `search_text` | ≈ 17 КБ + I/O поиска |
| Голосовые | 30 голосовых | ≈ **50 КБ** (обычно), до нескольких МБ, если подряд идут часовые записи |
| Сводки чатов | 20 записей `chatSummaries` | ≈ **170 КБ** (в документе лежит массив `messageIds`) |
| Карточка сообщения | сообщение, ответ, голосовое, до 20 сводок | ≈ **3–10 КБ** |

Для сравнения: один проход старой синхронизации читал около 110 МБ, а при
работе раз в минуту выходило ~4,5 ГБ в день. Вечер активного просмотра
(100 действий) теперь стоит порядка 2–5 МБ.

Convex считает I/O по своим правилам: размер документа в хранилище плюс
накладные расходы на индекс. Поэтому `readBytes` — оценка, а не счёт.

## Ограничения

- «Последние сообщения» по всем чатам упорядочены по времени сохранения в
  Convex (`_creationTime`). Импортированная история появляется там, где её
  импортировали. Порядок по дате сообщения и фильтр по датам работают внутри
  выбранного чата. Чтобы сортировать общую ленту по дате, нужен индекс по
  `ts`, а его первичное построение прочитает всю таблицу.
- Список чатов строится из `chatIndexStats`. Чаты, где есть только голосовые
  (личные и бизнес-чаты), в боковой панели не появятся, но видны в разделе
  «Голосовые».
- Количество сообщений в чате берётся из счётчиков `chatIndexStats`. Общего
  количества по фильтру нет: для него пришлось бы читать все строки.
- Фильтров по автору и типу сообщения больше нет: без индекса они требуют
  полного сканирования.
- Раздела «База данных» (просмотр любых таблиц) больше нет: он работал через
  `_system/cli/tableData`.

## Запуск

Нужен Python 3, стандартная библиотека. Функции из `convex/dashboard.ts`
должны быть задеплоены на тот же deployment (сейчас dev `necessary-elk-73`).
Пока их там нет, страница покажет ошибку «Convex не выполнил запрос».

`connection.json` (0600, вне git):

```json
{"url": "https://<deployment>.convex.cloud", "key": "<admin key>"}
```

Admin key нужен, чтобы вызывать internal-функции. Ключ даёт и право записи,
но сервер вызывает только `/api/query` и только функции `dashboard:*` из
белого списка. В браузер ключ не передаётся.

Переменные окружения:

| Переменная | По умолчанию |
|---|---|
| `DASHBOARD_CONNECTION` | `connection.json` рядом с `server.py` |
| `DASHBOARD_HOST` / `DASHBOARD_PORT` | `10.10.10.1` / `8511` |
| `DASHBOARD_ALLOWED_HOSTS` | `10.10.10.1,localhost,127.0.0.1` |
| `DASHBOARD_ALLOWED_NETWORKS` | `127.0.0.0/8,10.10.10.1/32,10.20.20.0/24,192.168.1.0/24,192.168.2.0/24` |

Разовый локальный запуск:

```sh
DASHBOARD_CONNECTION=/root/served/tg-history-dashboard/connection.json \
DASHBOARD_HOST=127.0.0.1 DASHBOARD_PORT=8599 python3 dashboard/server.py
```

Тесты (Convex подменён заглушкой, сеть не нужна):

```sh
cd dashboard && python3 -m unittest -v
```

## Перенос на сервер (только после одобрения Ильи)

Юнит `tg-history-dashboard.service` сейчас остановлен и отключён. Не включать
его, пока не задеплоены функции и Илья не одобрил запуск.

1. Задеплоить `convex/dashboard.ts` вместе с остальным кодом ветки, которая
   стоит на deployment.
2. Отложить старую версию (локальную базу не удалять без отдельного решения):
   `mv /root/served/tg-history-dashboard /root/served/tg-history-dashboard.old-sync`
3. Скопировать новую:
   `install -d -m 0700 /root/served/tg-history-dashboard && cp -r dashboard/server.py dashboard/static /root/served/tg-history-dashboard/`
   и вернуть `connection.json` (0600) из старой папки.
4. Заменить юнит на `dashboard/tg-history-dashboard.service`. Новой версии не
   нужна запись на диск, поэтому в нём нет `ReadWritePaths`.
   `systemctl daemon-reload`
5. После одобрения: `systemctl enable --now tg-history-dashboard`, затем
   `curl http://10.10.10.1:8511/health` (этот запрос не обращается к Convex).

Откат: `systemctl disable --now tg-history-dashboard`. Старую версию с фоновой
синхронизацией обратно не включать.
